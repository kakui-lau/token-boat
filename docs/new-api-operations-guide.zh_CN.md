# New API 聚合平台运营手册（TOC + TOB）

> 适用场景：从零搭建一个面向个人开发者（TOC）和企业客户（TOB）的多上游 AI API 聚合平台。  
> 本文不使用任何现有生产配置或历史数据。示例中的分组、倍率、价格和渠道名称均为建议模板。

## 1. 运营目标

平台不是简单转发 API，而是在上游供应商与下游客户之间提供四项价值：

1. **统一接入**：统一域名、API Key、模型名称和 OpenAI 兼容协议。
2. **稳定性**：同一模型接入多个上游，支持负载均衡、故障切换和自动禁用。
3. **价格管理**：采购价、销售价、客户折扣相互独立，并持续监控毛利。
4. **企业能力**：为 TOB 提供合同价、专属额度、并发保障、账单和技术支持。

首期不要追求模型数量。优先做到：

- 核心模型至少有两个可替代上游；
- 用户看到的模型名称、价格和实际扣费一致；
- 每一笔调用能够追踪到用户、API Key、模型和实际渠道；
- 上游价格变化后能在一个工作日内完成评估和更新；
- 渠道故障不会造成大面积调用失败或错误扣费。

---

## 2. 必须先理解的四个对象

### 2.1 用户

用户是平台账号。每个用户只有一个所属分组，例如：

- `default`：普通 TOC 用户；
- `business`：标准 TOB 客户；
- `enterprise_acme`：有独立合同价格的企业；
- `staff`：内部员工。

用户分组表示客户身份。

### 2.2 API Key（令牌）

API Key 是用户调用接口使用的 `sk-...` 密钥。一个用户可以创建多个 API Key，每个 Key 可以设置：

- 有效期；
- 可用额度；
- 可用模型；
- IP 白名单；
- 计费分组；
- 是否允许 `auto` 跨分组重试。

API Key 分组表示这把 Key 请求时使用的计费和渠道分组。首期建议不要让普通用户看到多个线路，默认使用 `default` 或 `auto`。

### 2.3 渠道

渠道代表一个合法获得授权的上游账号、API Key 或企业接口。渠道决定：

- 实际请求发给谁；
- 支持哪些模型；
- 对哪些分组开放；
- 模型名称如何映射；
- 优先级和同级权重；
- 失败后是否自动禁用。

### 2.4 模型

模型是下游用户看到并请求的标准化名称，例如：

```text
openai/gpt-5.4
anthropic/claude-sonnet-4.6
google/gemini-3.1-pro
bytedance/seedance-2.0
```

同一个平台模型可以映射到多个上游的不同名称。用户始终请求平台标准名，渠道负责映射到上游名。

## 3. 建议的首期分组设计

分组同时参与用户身份、API Key 选择、渠道权限和价格倍率。分组过多会显著增加误配置风险。

建议首期只建立以下分组：

| 分组 | 用户 | 用途 | 建议倍率 |
|---|---|---|---:|
| `default` | TOC 用户 | 标准公开服务 | `1.0` |
| `business` | 标准 TOB | 企业标准服务 | `1.0` |
| `staff` | 内部人员 | 内部测试与运维 | 按内部政策 |

只有客户确实存在独立合同价、独立渠道或 SLA 时，才增加：

```text
enterprise_<客户简称>
```

例如：

```text
enterprise_acme
enterprise_demo
```

### 3.1 不建议首期建立的分组

- 不要仅为了限速建立 `trial` 分组，试用额度和频率限制更适合控制试用。
- 不要把每个上游供应商建成一个用户可选分组。
- 不要同时建立大量 `vip`、`svip`、`pro`、`premium`，除非每一组有明确权益。
- 不要用分组倍率表示上游给平台的采购折扣。

### 3.2 特殊规则

首期建议：

```json
特殊倍率规则 = {}
特殊可用分组规则 = {}
```

只有出现“某类客户可以选择多条服务线路，并且每条线路价格不同”时才使用特殊规则。

## 4. 模型治理

### 4.1 模型名称规范

统一采用：

```text
provider/model-id
```

规则：

- 全部小写；
- 使用 `/` 分隔供应商和模型；
- 使用 `-`，避免空格和下划线；
- 保留官方版本号；
- 不把上游渠道品牌、折扣或线路写入模型名；
- 同一模型在所有渠道使用同一个平台名称。

模型名称的详细规则见 [模型命名规范](./model-naming-conventions.zh_CN.md)。

### 4.2 模型准入条件

新模型进入模型广场前必须同时满足：

1. 至少有一个已测试可用的渠道；
2. 请求与响应格式已确认；
3. 平台名称与上游映射已配置；
4. 销售价格已配置；
5. Token、按次或动态计费方式已确认；
6. 流式、工具调用、图片、音频或异步任务能力已测试；
7. 错误调用不会产生错误扣费；
8. 模型元信息、供应商、类型和标签已补全。

### 4.3 推荐模型组合

不要把上游返回的全部模型直接开放。建议每个能力保留少量主力模型：

| 能力 | 建议数量 | 运营原则 |
|---|---:|---|
| 通用文本 | 4–8 | 高端、均衡、低价各一档 |
| 编程 | 2–4 | 强调上下文、工具调用和稳定性 |
| 推理 | 2–4 | 明确展示输出价格和思考 Token 规则 |
| 图片 | 2–4 | 按质量、尺寸或 Token 正确计费 |
| 视频 | 2–4 | 明确时长、分辨率、输入素材和失败退款 |
| Embedding/Rerank | 2–4 | 低价、稳定、批量能力优先 |
| 语音 | 2–4 | 区分输入、输出、时长或字符计费 |

### 4.4 模型生命周期

每个模型使用以下状态：

```text
候选 → 内测 → 上线 → 观察 → 下线
```

下线顺序：

1. 停止新增客户使用；
2. 公告替代模型和下线日期；
3. 从模型广场隐藏；
4. 保留短期兼容映射；
5. 确认无调用后移除渠道模型；
6. 最后清理定价和元信息。

不要先删价格再删渠道，否则可能造成无法计费或错误回退。

## 5. 多上游渠道管理

### 5.1 一个渠道只表达一个清晰的采购单元

建议命名：

```text
<供应商>-<账号/区域>-<用途>
```

例如：

```text
vendor-a-jp-primary
vendor-a-us-backup
vendor-b-global-primary
official-openai-enterprise
```

如果同一上游对不同模型给出不同折扣，而你需要不同的路由优先级，应拆成不同渠道或渠道标签，避免一个全局优先级错误影响所有模型。

### 5.2 渠道上线检查

每条新渠道必须记录：

- 合同主体和上游联系人；
- 上游类型、Base URL、区域；
- API Key 归属与到期时间；
- 结算币种和付款方式；
- 模型清单；
- 模型映射；
- 上游公开价；
- 实际折扣；
- 有效采购价；
- 并发、RPM、TPM 限制；
- 余额告警方式；
- 服务条款是否允许转售；
- 数据保留、训练和隐私条款；
- 故障及退款规则。

### 5.3 优先级和权重

New API 的基本路由逻辑：

- **优先级越高越先使用**；
- 相同优先级下，按照权重分配流量；
- 高优先级不可用或重试后，进入较低优先级；
- `auto` 分组可以按配置顺序跨分组寻找可用渠道。

推荐三级：

| 层级 | 作用 | 配置建议 |
|---|---|---|
| P100 | 主渠道 | 成本、质量和稳定性综合最优 |
| P50 | 同区域备用 | 稍贵但协议兼容、切换风险低 |
| P10 | 灾备渠道 | 成本可能较高，只用于兜底 |

不要单纯因为某上游便宜就给最高优先级。应计算风险调整后的有效成本。

### 5.4 风险调整成本

维护一份独立于用户售价的采购成本表：

```text
有效采购成本
= 上游目录价 × 合同折扣
+ 汇率缓冲
+ 支付/税费
+ 失败不可退成本
+ 运维风险准备
```

建议渠道评分：

```text
渠道总分
= 成本得分 × 40%
+ 成功率 × 25%
+ 延迟 × 15%
+ 质量一致性 × 10%
+ 额度与并发 × 10%
```

权重可以按业务调整，但不能只比较目录价。

### 5.5 多渠道流量策略

推荐：

- 主渠道承担 70%–90% 流量；
- 第二渠道保持 10%–30% 活跃流量，确保灾备长期可用；
- 新渠道先灰度 1%–5%；
- 不要让备用渠道长期零流量，否则故障时无法确认真实可用性；
- 上游价格变化、错误率升高或质量变化时调整优先级，而不是立即删除渠道。

## 6. 定价体系

### 6.1 核心原则：采购价与销售价分离

上游给平台的折扣属于采购成本，不能直接写进分组倍率。

```text
上游折扣 → 决定渠道成本和路由优先级
模型销售价 → 决定用户扣费
客户折扣 → 通过合同价或分组倍率实现
```

同一用户请求可能被路由到不同上游，但用户售价应保持稳定，除非产品明确销售不同质量线路。

### 6.2 定价基准

对每个模型维护三类价格：

| 价格 | 含义 |
|---|---|
| 官方目录价 | 模型厂商公开价格 |
| 平台采购价 | 考虑渠道折扣、币种和附加成本后的真实成本 |
| 平台销售价 | 用户实际看到并支付的价格 |

推荐销售价公式：

```text
最低销售价 = 风险调整采购成本 ÷ (1 - 目标毛利率)
最终销售价 = 市场可接受价与最低销售价综合确定
```

示例：

```text
风险调整成本：$0.80
目标毛利率：20%
最低销售价：$0.80 ÷ 0.80 = $1.00
```

### 6.3 建议毛利区间

以下仅用于建立制度，不代表具体模型价格：

| 产品 | 建议目标毛利 |
|---|---:|
| TOC 标准按量 | 15%–30% |
| TOC 充值活动 | 活动后仍应保留 8%–15% |
| 标准 TOB | 10%–25% |
| 大客户承诺量 | 5%–15% |
| 高风险视频/图片 | 20%–35% |
| 稀缺或高保障线路 | 25%–40% |

毛利必须基于实际被选中的渠道成本计算，而不是只看最便宜渠道。

### 6.4 三种计费方式

#### Token 按量计费

适用于文本、Embedding、Rerank 以及能够准确返回 Usage 的模型。

如果模型输入、输出价格固定，可使用模型倍率和补全倍率：

```text
费用 ∝
(输入 Tokens + 输出 Tokens × 补全倍率)
× 模型倍率
× 分组倍率
```

更推荐在运营表中直接维护真实的：

```text
输入价（USD / 1M Tokens）
输出价（USD / 1M Tokens）
缓存读取价
缓存写入价
图片/音频 Token 价
```

#### 按次计费

适用于每次请求成本固定的图片、视频或工具：

```text
费用 = 单次价格 × 分组倍率
```

#### 动态表达式计费

适用于价格由请求条件决定的模型，例如：

- 视频是否包含参考视频；
- 输出分辨率；
- 视频时长；
- 图片质量和尺寸；
- 长上下文档位；
- 缓存类型；
- 时间或请求参数规则。

动态计费必须遵守 [计费表达式说明](../pkg/billingexpr/expr.md)，并测试预扣、结算和退款全链路。

### 6.5 分组倍率怎么用

分组倍率是销售价格调整，不是采购折扣。

推荐初始状态：

```json
{
  "default": 1.0,
  "business": 1.0,
  "staff": 1.0
}
```

先直接把模型销售价配置正确。等 TOB 合同明确后，再为企业组设置统一折扣。

例如基础销售价为 `$10`，企业合同九折：

```text
business 倍率 = 0.9
企业价格 = $10 × 0.9 = $9
```

如果不同模型折扣不同，不应使用统一分组倍率，应使用独立企业价目表或单独模型销售配置。

### 6.6 充值与销售倍率

充值赠送会改变实际毛利。

例如用户支付 `$100` 获得 `$110` 余额，相当于销售收入倍率：

```text
100 ÷ 110 = 0.9091
```

模型表面毛利 20%，叠加充值赠送后可能只剩约 12%。所有优惠必须统一折算进“净销售收入”。

禁止同时无测算地叠加：

- 模型低价；
- 分组折扣；
- 充值赠送；
- 优惠码；
- 订阅折扣；
- 渠道失败不可退款成本。

### 6.7 汇率

上游使用人民币、美元或其他币种时：

- 采购成本统一折算为 USD 或平台记账币种；
- 不使用实时汇率直接改变用户价格；
- 设置 2%–5% 汇率缓冲；
- 每周复核，达到阈值后批量调整；
- 每次调整保留旧价格、生效时间和审批记录。

## 7. TOC 产品设计

推荐提供：

1. 注册赠送小额试用；
2. 按量充值；
3. 少量清晰的订阅包；
4. 模型广场公开价格；
5. API Key 自助管理；
6. 用量日志和余额告警；
7. 文档、示例和社区支持。

### 7.1 TOC 风控

- 注册、登录、验证码、充值回调和 API 请求分别限流；
- 认证刷新接口不能使用会阻断正常登录的通用严苛限流；
- 试用用户限制并发、RPM、每日额度和高成本模型；
- API Key 支持 IP 白名单、模型白名单、额度和过期时间；
- 高成本视频和图片请求必须先校验参数上限；
- 余额不足时在调用上游前拒绝；
- 生成失败按明确规则退款，不能只依赖上游状态文本。

## 8. TOB 产品设计

标准 TOB 服务应包含：

- 企业账号和多个 API Key；
- 月度账单与调用明细；
- 预算、余额和用量告警；
- 固定模型名称和兼容策略；
- SLA 与故障通知；
- 发票和合同；
- 数据处理与隐私说明；
- 专属技术支持；
- 可选 IP 白名单和专属并发。

### 8.1 TOB 定价方式

建议从简单到复杂：

1. **标准企业价**：平台公开价 × 企业统一倍率；
2. **承诺量阶梯价**：达到月度消费后执行下一周期折扣；
3. **预付资源包**：按有效期和总额度销售；
4. **专属模型价目表**：仅用于大型合同；
5. **专属线路**：客户确实购买官方直连、区域或 SLA 时才建立。

不要口头承诺永久低价。合同应明确：

- 价格有效期；
- 上游调价后的通知和调整机制；
- 汇率变化；
- 模型下线与替代；
- 失败请求退款；
- 超额用量；
- 最低消费或预付余额；
- SLA 排除项。

## 9. 配置顺序

新平台按以下顺序配置：

### 第一步：全局基础配置

- 站点名称、域名、Logo；
- 邮件和通知；
- 计价币种；
- `QuotaPerUnit`；
- 充值、支付回调和签名；
- 注册赠送和邀请策略；
- 日志保留；
- Redis、数据库备份和监控。

`QuotaPerUnit` 上线后不应随意修改，它影响余额与价格换算。

### 第二步：分组

- 建立 `default`、`business`、`staff`；
- 配置用户可用分组；
- 配置自动分组顺序；
- 暂不配置特殊倍率和特殊可用规则；
- 确认普通用户创建 API Key 时只看到预期分组。

### 第三步：模型目录

- 建立标准模型名称；
- 补充模型元信息；
- 配置供应商、能力、上下文、标签；
- 确定每个模型的计费方式；
- 配置销售价格；
- 暂不公开没有渠道或没有价格的模型。

### 第四步：渠道

- 创建主渠道；
- 配置模型映射；
- 配置分组；
- 单模型测试；
- 增加备用渠道；
- 配置优先级和权重；
- 开启合理的自动禁用；
- 小流量灰度。

### 第五步：支付与套餐

- 先完成按量充值闭环；
- 再建立 TOC 订阅包；
- 最后建立 TOB 合同价和资源包；
- 用真实订单验证支付金额、到账额度、退款和对账。

### 第六步：公开

- 模型广场只展示已验证模型；
- 服务条款、隐私政策和退款政策上线；
- 文档说明请求地址、鉴权、模型名、错误码和限流；
- 发布状态页与支持入口。

## 10. 日常运营制度

### 每日

- 渠道成功率、P95 延迟和自动禁用；
- 上游余额与额度；
- 大额消费和异常增长；
- 失败任务与退款；
- 登录、充值和 API 429/5xx；
- 毛利异常模型。

### 每周

- 上游对账；
- 按模型、渠道、客户计算收入、成本和毛利；
- 复核汇率；
- 测试备用渠道；
- 检查无价格模型和无渠道模型；
- 检查重复、错误或已下线模型名；
- 复核渠道权重与优先级。

### 每月

- TOB 账单和合同额度；
- 上游账单差异；
- 模型销售价格；
- 渠道供应商评分；
- 低毛利或亏损模型；
- 订阅包实际消耗率；
- 数据库备份恢复演练；
- API Key、管理员权限和安全审计。

## 12. 调价 SOP

上游价格变化时：

1. 记录上游公告、币种、生效时间和受影响模型；
2. 更新采购成本表；
3. 计算所有渠道的新有效成本；
4. 检查当前销售价和充值优惠后的真实毛利；
5. 决定调整渠道优先级还是调整销售价；
6. 在测试环境验证计费；
7. 对 TOB 检查合同通知期；
8. 发布调价公告；
9. 到生效时间一次性更新；
10. 用小额真实请求核对用户扣费与上游账单；
11. 观察 24 小时毛利和异常日志。

禁止只修改前端展示价格。必须确认后端实际扣费配置同步生效。

---

## 13. 渠道故障 SOP

1. 判断是单 Key、单模型、单区域还是供应商整体故障；
2. 自动禁用异常渠道或 Key；
3. 确认备用渠道已承接流量；
4. 检查备用渠道余额、并发和成本；
5. 对失败请求执行补偿或退款；
6. TOB 达到通知阈值时发送故障通知；
7. 上游恢复后先小流量验证；
8. 逐步恢复权重；
9. 记录故障时长、客户影响、成本与改进项。

## 14. 上线验收清单

### 计费

- [ ] 每个公开模型都有唯一计费方式；
- [ ] 输入、输出、缓存、图片、音频和任务价格正确；
- [ ] 分组倍率不会导致低于成本；
- [ ] 充值赠送后仍满足最低毛利；
- [ ] 预扣、结算、失败退款均已测试；
- [ ] 模型广场价格与实际扣费一致。

### 渠道

- [ ] 核心模型至少两个上游；
- [ ] 模型映射正确；
- [ ] 优先级和权重符合成本与 SLA；
- [ ] 自动禁用和恢复策略已测试；
- [ ] 备用渠道有持续探活流量；
- [ ] 上游余额告警已配置。

### 模型

- [ ] 名称符合规范；
- [ ] 没有重复别名；
- [ ] 元信息完整；
- [ ] 能力标签真实；
- [ ] 不支持的参数会被拒绝或正确转换；
- [ ] 下线模型有替代方案。

### 用户与安全

- [ ] TOC/TOB 分组权限正确；
- [ ] API Key 可限制模型、额度、IP 和有效期；
- [ ] 登录、注册、刷新和 API 限流相互独立；
- [ ] 管理员权限最小化；
- [ ] 密钥、数据库和日志不泄露敏感信息；
- [ ] 数据库备份已完成恢复验证。

### 法务与支持

- [ ] 上游授权允许当前业务模式；
- [ ] 服务条款、隐私政策、退款政策已发布；
- [ ] TOB 合同包含调价、SLA 和模型变更条款；
- [ ] 支持入口、状态页和故障通知可用。

## 15. 推荐的首期落地方案

如果现在从零开始，建议：

```text
分组：
  default
  business
  staff

特殊倍率：
  {}

特殊可用分组：
  {}

渠道：
  每个核心模型 1 个主渠道 + 1 个备用渠道
  主渠道按风险调整成本选择
  同优先级使用权重灰度

模型：
  首期公开 15–30 个
  每种能力只保留主力模型
  统一 provider/model-id 命名

价格：
  先配置准确的平台标准销售价
  default = 1.0
  business 合同明确后再设置折扣
  上游采购折扣只进入成本表，不进入用户分组倍率

TOC：
  小额试用 + 按量充值

TOB：
  标准企业价 + 预付余额
  大客户再增加专属组和合同价
```

这个结构最容易运营、对账和排错。等实际业务证明需要多线路、多等级或代理商体系后，再启用 `auto` 跨分组、特殊可用分组和特殊倍率。
